EA-SYS · Platform readiness

Two tenants, one platform

Two separate companies now run on the same EA-SYS installation, at the same web address, and neither can see a single row of the other's data. The separation is enforced by the database itself, not by application code that could be bypassed by a bug.

What you are looking at

Every screenshot below comes in a pair. The left is Acme, the right is Globex, always in that order. The two tenants were given deliberately identical data — both run an event called “Annual Summit”, at the identical web address /e/annual-summit — because identical inputs are what make the difference in the output mean something.

The mechanism is a Postgres feature called row-level security. Rather than trusting every query in the application to remember to filter by customer, the database refuses to return another tenant's rows at all. If a developer writes a query that forgets the filter, it returns nothing rather than everything. The safe direction is the default.

The same address, two different events

This is the claim that matters most, and the one a screenshot cannot make on its own, because an image has no address bar. The exact URL that produced each image is printed above it. Same page, same form, different event, different venue, different prices.

Each tenant sees only its own workspace

Signed in as each company's administrator. Both accounts reach the same application, and each reports one event in its workspace. The colour difference is not decoration: each tenant sets its own brand colour, and the interface picks it up. The sidebar is the tenant's own: our internal documentation and infrastructure panels are not on it.

And only its own records

The contact book is shared infrastructure holding both companies' rows in one table. Each administrator sees a count of one, and it is their own.

An unrecognised address gets nothing

The negative case, and the one most easily forgotten. Both tenants hold an event on this exact address. A visitor arriving on a web address we have not registered is not quietly served whichever one happened to be found first.

What is not finished

Stated plainly, because the gaps decide the timeline and every one of them is already written down and scheduled.

Three things stand between this and a paying customer

  • The events table is not yet protected at the database layer. It is the row flagged in the table above. Events are still separated correctly by application code, which is how the whole system worked until now, but it does not yet have the database as a second line of defence. That work is understood and sized: roughly 340 places in the code. It does not block the first customer, who has nobody to be separated from. It must be done before the second.
  • There is no way to create a customer yet. No sign-up, no administration screen for adding a company, no self-service. Both tenants here were created by a script. This is the largest remaining piece of actual product work.
  • This is a rehearsal environment, not a live one. It runs on a developer machine. The production platform needs its own server and database, plus backups, monitoring and alerting, before any customer is onboarded.

What the rehearsal caught

Building this rehearsal found several real faults in the isolation machinery, and neither announced itself. Both produced empty screens rather than error messages.

One made every protected table return nothing at all. Another, worse, meant every public event page would have shown “Registration Closed” — the single most important flow in the product, dead on arrival, on a page that looked perfectly healthy. A third had our own internal documentation and server metrics reachable by a customer's administrator.

All of them are fixed, and there is now an automated check covering thirteen domains that fails if any of them is reintroduced. The reason this is worth telling you rather than burying: they were found on a laptop, at no cost, rather than on a paid server in front of a customer. That is what the rehearsal was for, and it is the argument for doing it this way again.

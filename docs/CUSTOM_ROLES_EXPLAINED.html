EA-SYS · October 2026

From roles to permissions

How the app used to decide what each person may do, how it decides now, and what we changed to get there.

The question the app asks all the time

EA-SYS is a website for running events. Many people sign in to it: the people who organise events, desk staff who check visitors in, sales staff, HR staff, and more.

Every time someone clicks a button, the website's server gets a request, for example "show the list of people registered for this event" or "delete this speaker". Before it does anything, the server must answer one question:

Is this person allowed to do this?

This document is about how the server answers that question.

Before: roles

Every account had exactly one role. A role is a name stored on the account, such as ADMIN, ORGANIZER, MEMBER, ONSITE or WEBINARS. There were 11 role names.

The code checked the name directly. Many files contained lines like this:

if (role is "ADMIN" or role is "ORGANIZER") {
  allow it
} else {
  refuse it
}

This worked, but it had problems:

  • The same list of names was written in many places. If one file forgot a role, that role could do something it should not, or could not do something it should.
  • A new role meant editing hundreds of files. Adding HR_USER meant checking every list in the app by hand.
  • Nobody could make a role in between. If a team needed "can see registrations and send emails, but nothing else", the only option was to write new code.

After: permissions

A permission is one small, named action. Its name says what it allows, for example:

  • registrations.read: see the list of registrations
  • registrations.export: download that list as a file
  • finance.view: see money (prices, payments, invoices)
  • barcode.view: see the entry barcodes that let a visitor through the door

The app has one list of all permissions, called the catalogue. It holds 161 permissions.

A role is now just a list of permissions. ORGANIZER is a list of 131 permissions. HR_USER is a list of 2.

The code no longer asks "what is your role name?". It asks one function, called can():

can(person, "registrations.export", thisEvent)  →  yes or no

Every request on the server now starts with a check called requirePermission(), which asks can() and refuses with an error if the answer is no.

Scope: which events a permission covers

Some permissions are about one event, like editing that event's speakers. For those, a role also says which events the permission covers. This is called the scope. There are three:

ScopeMeansUsed by
ALLevery event in the organisationOrganizer, Member
ASSIGNEDonly events this person was added toOnsite desk staff
WEBINARonly events of the type "webinar"Webinars team

So can() needs to know the event too. A Webinars person asking to edit speakers on a webinar gets "yes". The same person asking about a conference gets "no".

Custom roles

Because a role is now just a list, an administrator can make a new one in Settings → Roles without anyone writing code. A custom role:

  • starts from a base role (one of the built-in ones), and
  • adds extra permissions by ticking boxes.

Some rules stop a custom role from becoming too powerful:

  • Admin-only permissions. Four permissions can never go into a custom role: managing roles, managing users, managing API keys, and connecting AI tools (roles.manage, users.manage, apiKeys.manage, mcp.connect).
  • Areas. Each base role works in certain parts of the app, called areas (events, CRM, HR, organisation settings). Extra permissions must fit the base role's areas. A sales account cannot be given event permissions this way.
  • No wider than you. You can only hand out permissions you hold yourself, and you cannot change your own role.

How we moved, step by step

The app was already running real events, so we could not switch everything at once. We moved in steps and checked each one before the next.

  1. Phase 0 · Sep 30

    Tidy the old lists

    We found every list of role names, made each one an "allow list" (a role not on the list is refused), and added a test that fails if someone writes a new list inside a file.

  2. Phase 1 · Sep 30 to Oct 1

    Write the catalogue and the built-in roles

    We wrote all 161 permissions, and wrote each built-in role as a list of permissions. Then a parity test asked both the old checks and the new can() the same questions, for every role. Every answer had to match.

  3. Phase 2 · Oct 1 to Oct 5

    Change every server route

    A route is one address on the server that answers requests, like /api/events/…/speakers. We changed 335 route files to start with requirePermission(). Before changing each group, we recorded what every role got back (allowed, refused or not found) in a table called the route matrix, so any change in behaviour showed up as a test failure.

  4. Phase 3 · Oct 5

    Screens and the AI agent

    Buttons on the screens now ask the same permissions (through useCan()), so a person only sees buttons that will work. The AI agent checks the same permission as the matching route before it runs a tool.

  5. Phase 5 · Oct 5

    API keys with a role

    An API key is a password that lets another program use EA-SYS. A key can now be given a role, so it can do only what that role allows.

  6. Phase 4 · Oct 6

    A real table for desk staff

    Which onsite staff work at which event used to be a list hidden inside the event's settings. It moved into its own database table, EventStaffAssignment, so the server can look it up quickly and correctly.

  7. Oct 6

    Switch it on

    Custom roles were hidden behind a feature flag, a setting that turns a feature on or off without new code. On October 6 the flag CUSTOM_ROLES_ENABLED was turned on in production.

  8. Phase 6 · Oct 6 to Oct 7

    Remove the old code

    We deleted every old role-name check. To prove nothing changed, a program signed in as six different roles, opened 99 pages each, and compared what it saw before and after. Access was the same. A snapshot test now saves the full permission list of every built-in role, so any future change to a role shows up and must be approved.

  9. Oct 7

    Check it with fresh eyes

    Five separate reviewers each searched one part of the system for mistakes. They found 3 serious problems and 7 medium ones. All were fixed, each with a test that fails if the problem comes back.

What the final review fixed

Most of these were older than the move to permissions. Looking at everything at once is what found them.

ProblemFix
Changing a registration's email also changed the sign-in email of the account behind it, even a staff account. That could let someone take over an admin account.A staff account's sign-in email can no longer be changed from an event screen.
When an existing account was made into staff, it kept its old password, which a stranger might have chosen.The account gets a new password (set by the admin, or by the person through an invitation email).
Some AI tools checked the event in the request, then changed records in a different event.Each tool now only touches records in the event it was allowed to use.
Some places returned entry barcodes or money to people without barcode.view or finance.view.The server removes those fields before sending the answer.
A Webinars user could change certificate and reimbursement settings through the general event settings.Those settings can only be changed on their own screens, with their own permissions.
The "for the sales team" download did not ask for registrations.export.It does now, and the Export button is hidden from people without it.
Someone allowed to invite users could invite a person with more power than they had.You can only invite people to a role whose permissions you hold.

What people using the app notice

  • For the built-in roles, almost nothing changed. The 99-page comparison proved that.
  • Administrators can create custom roles in Settings → Roles. Approval chains moved to their own Approvals tab.
  • The WEBINARS role is retired. The webinar team are now MEMBER accounts with a custom role called "Corporate" that adds event editing.
  • A few deliberate changes: the Webinars team no longer sends certificate emails, Members can no longer download the "for the sales team" file, and a promoted account must set a new password.

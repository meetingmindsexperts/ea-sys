Code Review: Email templates, tokens and senders

September 18, 2026. Three-lens adversarial review (token resolution, template association, sender surface), read-only. Every claim was verified in source at commit 01bbce0b; line numbers are from that commit. Production figures are read-only queries run the same day.
Status, September 18, 2026. Phase 0 shipped the same day (owner: "Phase 0 only"): findings 1, 2, 3, 4, 6, 9, 10 and 13 are fixed and pinned by tests, with the raw-key default and the bulk payment block mutation-verified. Findings 5, 7, 8, 11 and 12 and the lows are recorded under ROADMAP, "Email templates, tokens and senders", as Phases 1 to 3, each an owner decision.

1. Verdict in four lines

  • The core is not spaghetti. One send choke point (sendEmail), one render engine with the token normalizer and the unresolved-token refusal, one template resolver (getEventTemplate), one branding wrapper with the global event variables, and shared builders for every complex block (speaker context, agreement, RSVP, survey, travel grant, barcode, payment reminder, abstract variables). These work and should not be touched.
  • The spaghetti is at the edges, in three layers. The association layer (how an email type becomes a slug) exists as five hand-copied maps. The token contract (which tokens a template may use, which are raw HTML, which a sender fills) is documentation only, with no test that a sender fills what its template uses. The sender surface pastes the same fifteen-to-thirty-line "resolve template, build variables, brand, send" block at about twenty-two sites, each with its own variable map.
  • Those edges have produced four real defects, one of them live on 23 of 29 events today, plus nine narrower ones. All are catalogued below with production counts.
  • Streamlining is worth doing, in phases. Fix the defects first (half a day, no structure change). Then give the templates a typed registry and the missing drift test (one to two days). Then collapse the senders onto one entry point (two to three days, one sender per commit). Do not fold the certificate cover or the agreement merges into the main engine.

2.3 Seeding and reset

Three seed sites with three rules: event create seeds all 35 rows fire-and-forget with no webinar filter (api/events/route.ts:226); the templates list GET seeds the missing ones with the webinar filter (email-templates/route.ts:56); MCP update_email_template seeds one row on demand without the token normalizer (agent/tools/communications.ts:305). The schema carries no origin marker, so an untouched seed and an organizer edit are indistinguishable; that is why the anchor-based repair scripts exist. Reset has two semantics: REST overwrites in place and refuses a custom slug; MCP deletes the row for any slug (finding 3).

3. Findings

No BLOCKER. Ranked by the damage a real organizer action does today. "Live" means the failure is reachable from the UI on production data now; "latent" means it needs an organizer edit or an MCP call that has not happened yet.

High 1. Bulk "Registration Confirmation" is refused on 23 of 29 events shipped live

src/lib/bulk-email.ts:388 (type to slug), :1700-1745 (base variables), :1864-1878 (the only place paymentBlock is set), src/lib/email.ts:1800 (default template uses {{paymentBlock}}), :728 (refusal)

The dialog offers "Registration Confirmation" for registrations and the Communications "Welcome Paid" tile defaults to it. It maps to the registration-confirmation slug, whose default body carries {{paymentBlock}}. Bulk fills that token only inside the payment-reminder branch and has no default for it, so on the confirmation type the token is never resolved. Since the September 11 guard every recipient is refused with unresolved_tokens: {{paymentBlock}}, a FAILED row and an error alert; before the guard the literal token was delivered.

Evidence

The 29 bulk confirmations ever sent (OSH Monthly Meeting, Oman Oncology Pharmacy) went out only because those two events had removed the token from their template. 23 of the 29 active registration-confirmation rows on production still carry it. No test renders a bulk confirmation.

Fix

Extract the payment block from sendRegistrationConfirmation into a builder and call it for the confirmation type, or route bulk confirmation through sendRegistrationConfirmation per recipient (which also restores the quote PDF and barcode the single path attaches). Pin with a test that renders the default template through bulk.

What to learn: the dialog, the tile and the server map all agreed that "confirmation" exists. None of them knew what the template needs. A map from type to slug is not a contract; the contract is "this sender fills these tokens", and nothing records it.

High 2. Reviewers' "Review Invitation" previews one template and sends another shipped latent

src/components/bulk-email-dialog.tsx:184 (option), :265 (preview maps non-speakers to custom-notification), src/lib/bulk-email.ts:386 (server maps invitation to speaker-invitation for every audience), precheck has no audience rule for it

Pick reviewers, choose Review Invitation, Preview shows the custom notification, Send delivers the speaker invitation: subject "Speaker Invitation", body "You're Invited to Speak". Nothing refuses it because the speaker tokens default to empty strings for every audience.

Evidence

Zero reviewer invitations have gone through bulk on production, so nobody has been hit. No test.

Fix

Key the slug on (type, audience) in one place, or remove the option for reviewers and point them at the reviewer pool invitation that already exists as a template.

High 3. MCP reset_email_template deletes an organizer's custom template shipped latent

src/lib/agent/tools/communications.ts:352-369; compare REST email-templates/[templateId]/route.ts:346-360

The MCP tool finds the row by slug and deletes it, with no system-slug guard. For a system slug the next read seeds the default again, which is the intent. For one of the eight custom slugs on production (joining instructions, chairperson invitation, faculty confirmation and so on) the row is the only copy, and the message still says "default will be used". REST refuses the same request.

Fix

Refuse custom slugs, and reuse the REST reset (overwrite in place) so the two cannot drift again. Pin with a test.

High 4. The automatic abstract decision email shows the reviewer-notes box as escaped source shipped latent

src/lib/abstract-notifications.ts:144-153 (builds reviewNotes as HTML, the comment says to register it raw), :386 (renderAndWrap called with no raw keys), src/lib/email.ts:1055 (DEFAULT_RAW_HTML_KEYS has no reviewNotes), src/lib/bulk-email.ts:1976 (bulk adds it, so the resend renders correctly)

Accept or reject an abstract with notes and the author receives <div style="background: #e0f2fe ..."><strong>Reviewer Notes: as visible text. The bulk "Resend Decision" for the same abstract renders the box. Same variable builder, two raw-key lists.

Evidence

Four decision emails have ever been sent on production, one with a stored body, none with notes, so no author has seen it yet. The variable is pinned by a test; the automatic render path is not.

Fix

Add reviewNotes to DEFAULT_RAW_HTML_KEYS (with claimSummary, presenterFeeBlock, rsvpLink, reimbursementLink, profileFormLink, which have the same shape) and pin the automatic path with a rendered assertion.

What to learn: a raw-key list hand-written at eleven call sites is a bug generator. The block builder knows its output is HTML; the knowledge belongs with the builder, not with every caller.

Medium 5. The registration completion email is hardcoded, unbranded and uneditable

send-completion-emails/route.ts:101 (hand-rolled from), :139 (hardcoded systemTemplates.registrationCompletion), src/lib/email.ts:3146

Every other attendee email carries the event's header image, footer and auto-CC and can be edited under Communications. The "Send Registration Forms" email after a CSV import carries none of that and cannot be edited. The emailTemplates block says "all callers will be migrated to use DB templates". Fix: a registration-completion entry in DEFAULT_TEMPLATES sent through the normal path.

Medium 6. Advertised tokens that one sender fills and another does notshipped

registrations/[registrationId]/email/route.ts:368-385 (no eventCity, eventCountry, organizerName, organizerEmail, eventDateRange), src/lib/email.ts:1548, :1699 (the editor advertises them), src/lib/bulk-email.ts:1175 (bulk fills them)

An organizer who adds {{eventCity}} to the Event Reminder, as the variable panel invites, sends fine from Communications and gets a refusal from the registration detail sheet. Same class: reviewScore is passed as undefined (abstract-notifications.ts:154) and receiptUrl as undefined (payment-confirmation-email.ts:167); renderTemplate treats undefined as unknown, so adding either token refuses every unscored decision or every offline payment confirmation. No production template uses these tokens on the affected slugs today. The "Dear {{title}} {{lastName}}" greeting that broke the survey thank-you on September 17 is still unfillable on document delivery, both reviewer notifies, the panelist invitation, the group confirmation and the reimbursement receipt.

Medium 7. Five senders format {{eventDate}} in the server's timezone, and caller-wins precedence hides the correct global value

bulk-email.ts:1164, registrations/.../email/route.ts:355, speakers/.../email/route.ts:160, payment-confirmation-email.ts:94, group-registration-service.ts:958; the tz-aware global block is email.ts:3656, spread under caller vars at :3777

An event stored as a Dubai after-midnight start (the create form stores wall-clock minus four hours) is the previous calendar day in UTC: the confirmation says the 3rd, every bulk reminder says the 2nd. Two of 39 production events have such a start, one upcoming. The same five sites render {{eventVenue}} as "venue" or "TBA" while the confirmation and the global block render "venue, city". The precedence test pins "caller wins", which is exactly what keeps this alive. Fix: delete the per-sender date and venue formatting so the global block is the only source.

Medium 8. "Disable" on a system template means "send the built-in text instead", and the preview does not say so

src/lib/email.ts:3696 (inactive row falls back to the default), editor copy at templates/[templateId]/page.tsx:318, preview at email-templates/[templateId]/route.ts:178-262 never checks isActive

An organizer who switches Registration Confirmation off to silence it during a test import finds every registrant still receives the built-in text, and the editor's Preview keeps rendering the disabled edits, so preview and send differ. For custom slugs the switch does what it says (hard refusal). Two meanings, one switch.

Medium 9. A scheduled saved-template send passes precheck and fails at fire timeshipped

src/lib/bulk-email.ts:1042-1053 (precheck loads the template only for the RSVP check) vs :1446-1455 (fire-time hard fail)

Schedule a saved template, deactivate it later: green "queued" toast, FAILED row a minute later, the class the precheck exists to prevent. Known and deferred since the communications round 2 review (A3). Fix: the precheck resolves the slug through the same rule as the send.

Medium 10. Certificate emails skip the event auto-CC and the bulk streamshipped

src/lib/certificates/bundle.ts:724-736 (never selects emailCcAddresses), :866-873 (branding hand-built), :948 (no cc, no stream)

Every other attendee email goes through brandingCc. A thousand-certificate blast also lands in transactional SES metrics. Fix: hand the rendered cover to the shared send half.

Medium 11. Three definitions of "is this a custom template"

bulk: emailType === "template" (bulk-email.ts:1424); registration route: !!templateSlug (:438); RSVP, dialog, editor: isCustomTemplateSlug

A REST call with templateSlug: "payment-reminder" on an event where that row is inactive hard-fails on the registration route and silently sends the built-in on bulk and the speaker route. UI surfaces only offer custom slugs, so this is REST and MCP reachable only.

Medium 12. Frozen seed copies with no provenance

prisma/schema.prisma (EmailTemplate has no origin, hash or customized-at field), clone/route.ts:445-456 (clone copies every row verbatim, hidden webinar rows included)

745 rows on production; nothing can say which are untouched seeds. A default-template improvement in code reaches no existing event, which is why {{abstractNumber}} and {{travelGrantBlock}} reached zero live copies and why anchor-based repair scripts exist. Accepted design so far, but it is the root of the "26 events hold a frozen copy" class of incident.

Medium 13. The agreement merges skip the token normalizer, with no guard behind themshipped

speaker-agreement.ts:1097, presenter-agreement.ts:100, saves at events/[eventId]/route.ts:87 store Tiptap output verbatim

An editor-mangled {{<span>speakerName</span>}} in Content, Speaker Agreement ships literally on the acceptance page and inside the PDF attached to every invitation. The email path is protected against exactly this since September 11; the agreement path is not.

Low

  • Twelve pasted || getDefaultTemplate(slug) fallbacks after getEventTemplate, which already falls back; each then rebuilds a minimal branding that cannot fire today.
  • Nine system slugs have no TEMPLATE_VARIABLES entry, so {{surveyLink}}, {{joinUrl}}, {{passcodeBlock}} and the webinar tokens are undiscoverable in the editor. The pasted-share-link incident of September 17 is what that looks like.

  • Bulk saved-template sends log templateSlug: "bulk-template", never the real slug; Email History cannot say which template went.
  • Settings, Email Templates classifies with a stale eight-slug list, so 27 system templates carry a "Custom" badge there.
  • refund-confirmation is seeded and editable on every event and has no sender.
  • Nine CTA-button builders with the same inline style; four approaches to the greeting name.
  • Seven inline copies of the "random token, hash, delete old, create" mint; only the agreement link is shared.
  • The registration single-send route accepts any templateSlug without the custom-slug classifier, and has no BCC or attachments while the speaker route and bulk do.

4. Already right: do not touch

  • sendEmail (email.ts:696-975): EmailLog row on every outcome, attachment names, the unresolved-token refusal, the circuit breaker, the admin alert, the non-production subject prefix. One choke point.
  • renderTemplate plus normalizeTemplateTokens plus findUnresolvedTokens, pinned by tests.
  • getEventTemplate with the active-row and default fallback and the branding load, plus renderAndWrap, the global event variables, wrapWithBranding, brandingFrom, brandingCc, renderMessageValue.
  • The block builders: buildSpeakerEmailContext (the one speaker source, used by bulk, single, preview, docx, the agreement merge), buildAbstractConfirmationVars and buildAbstractDecisionVars, buildPaymentReminderVars, buildAgreementBlock and mintSpeakerAgreementLink, buildRsvpButton and resolveRsvpLinkForPerson, buildTravelGrantBlock, buildEntryBarcode, ensurePersonalSurveyLink, buildEventDateTokens.
  • Bulk's per-recipient idempotency and abort, precheckBulkEmailViability behind both enqueue doors, and bulk-email-audience.ts shared by server and dialog.
  • On the certificate side, pickSingleCoverEmail and renderBundleEmailContent: one pipeline for the send and both previews. The per-certificate-template cover override is a legitimate layer above the per-event slug and should stay a separate vocabulary.

5. Proposal, in phases

Phase 0: the defects (about half a day, no structural change)

  1. Finding 1: build the payment block for bulk confirmation; test renders the default template through bulk.
  2. Finding 2: audience-keyed slug for invitation, or drop the reviewer option.
  3. Finding 3: MCP reset refuses custom slugs and reuses the REST reset.
  4. Finding 4: the six block keys join DEFAULT_RAW_HTML_KEYS; the automatic decision path gets a rendered test.
  5. Finding 6: ?? "" for reviewScore and receiptUrl; the registration route gains the location and organizer variables.
  6. Findings 9 and 10: precheck resolves the slug; the certificate send takes the event CC and the bulk stream.
  7. Finding 13: the two agreement merges and their save paths call the normalizer.

Blast radius: seven senders, each change a few lines, each with a test. Safe to ship as one gated push.

Phase 1: the contract (one to two days)

A single typed registry replaces DEFAULT_TEMPLATES: one entry per slug with kind (system or custom), recipient type, sendable-from surfaces, its bulk email type, its variables, its raw HTML keys, its default subject and bodies, and an optional preview fixture. From it derive SYSTEM_TEMPLATE_SLUGS, TEMPLATE_VARIABLES, DEFAULT_RAW_HTML_KEYS, the five type-to-slug maps, the dialog option lists, the Settings list and the preview samples, with a generated client-safe leaf so no server import leaks. Then the missing drift test: build each sender's variable map with fixtures and assert it covers its default template and its registry entry. That is the test that would have caught the survey thank-you refusal, finding 1 and finding 6 before an organizer did. Adding a system template becomes one entry instead of twelve files.

Phase 2: the senders (two to three days, one sender per commit)

One entry point, sendEventTemplatedEmail({ eventId, slug, recipient, vars, attachments, bcc, emailType, stream, triggeredByUserId, templateTransform }), doing getEventTemplate, the optional transform (the travel-grant and fee-block "append the token" trick, so those sites stop editing templates by hand), renderAndWrap, brandingFrom, brandingCc, and sendEmail with a full log context. Beside it, buildEventVars(event) (the global keys plus city, country, address, start date, one venue shape, all through buildEventDateTokens) and buildRecipientVars for a registration or a speaker row, extracted from bulk's generateEmailForRecipient. About sixteen senders collapse onto them, each losing fifteen to thirty lines; the two single-send routes become "resolve one recipient, build vars, send"; the completion email becomes a template (finding 5); finding 7 disappears because no sender formats a date any more. Must stay bespoke: sendRegistrationConfirmation (payment block, quote PDF, inline barcode), operator mail (not event-scoped) and CRM sponsor mail (its own reply model).

What can break on a live system: a missed raw key turns a block into escaped source (the July 16 MCP class); a missed transform drops the travel-grant token; a bug in the helper is a total event-mail outage. Mitigation: one sender per commit, the per-sender tests plus the unresolved-token suite as the net, and a real send to the owner's inbox per sender. Bulk and single-send switch from UTC dates to event-timezone dates and from "venue" to "venue, city", which is the fix but is visible.

Phase 3, owner call: seed provenance and the disable switch (schema, additive)

Nullable EmailTemplate.seedHash and customizedAt. Seed sites write the hash; PUT and MCP update stamp customizedAt; getEventTemplate serves the current code default when the row provably equals a default and was never customized, so a default improvement reaches untouched rows with no repair script; clone copies only customized rows. Backfill marks a row customized unless its content equals a current default (fail-safe, never overwrites an edit). And split the switch for system slugs into "use my edited version" and "use the built-in", keeping "disable" only for custom templates, with the editor preview rendering what the send would.

Do not do

  • Do not fold the certificate cover resolver into renderTemplate: every cover would change date format and the unknown-token contract, for no organizer benefit.
  • Do not fold the agreement merges in either; they should adopt the normalizer and the canonical escapeHtml and stay separate, because they feed a PDF and an acceptance page, not an email.

6. What to learn from this review

  • A documentation list is not a contract. TEMPLATE_VARIABLES tells the organizer what to type and tells no sender what to fill. The test that pins preview to template exists; the test that pins sender to template does not, and every refusal incident since September 11 sits in that gap.
  • A preview that renders the union of every sample is honest about the template and dishonest about the send. The editor shows a hundred and fifty resolvable tokens; each sender fills its own subset. The gap is invisible until the refusal.
  • Knowledge that lives with a caller drifts; knowledge that lives with the thing does not. Whether a block is HTML is a property of the block builder, not of the eleven senders that use it. Which template an email type maps to is a property of the type, not of five surfaces.
  • "Reset" that deletes is a different operation from "reset" that restores. Two surfaces gave one word two meanings, and only one of them was safe for organizer-created rows.
  • A seed with no provenance freezes. Once a row cannot say whether it was ever edited, every improvement to the default becomes a migration of organizer data, which is why it never happens.
Review method: three parallel read-only reviewers (token pipeline, template association, sender surface), each report re-verified against source by hand before inclusion, then read-only production queries for reach.
